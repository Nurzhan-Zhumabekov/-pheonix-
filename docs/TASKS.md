# Распределение задач

Команда из двух человек. Хакатон: старт сб 7 нояб 12:00, финиш вс 8 нояб 12:00, питчи с 13:00.
Контрольные 10 транскриптов открываются через 23 часа после старта (около 11:00 вс), стоп-код через 24 часа: последний коммит фиксируется для жюри.

## Стек

- Бэкенд на Rust (`axum`, `tokio`, `reqwest`, `serde`). Хранилище: JSON-файлы или SQLite в `storage/`.
- Интерфейс на HTML/CSS/JS, отдаётся бэкендом из `web/`. Rust для интерфейса знать не нужно.
- Каркас `backend/` готов: все эндпоинты из контракта работают, расчёт итога и версии чек-листа покрыты тестами. Judge подключён к модели через `.env` (Anthropic или OpenAI-совместимый API) и проверен на имитации API и на локальной модели через Ollama. Качество оценок на данных организаторов не измерено. Без `LLM_PROVIDER` отдаёт заглушку с `"mock": true`. Напарница уже может писать интерфейс против настоящего API, а не только против моков.
- Запасной план: если к 17:00 7 нояб. в Rust не работает сквозной путь «загрузить диалог, оценить один критерий через модель, получить JSON», бэкенд переписывается на Python FastAPI с тем же контрактом.

## Роли

> Обновление 7 нояб.: между агентами работа распределяется по [coordination/BOARD.md](coordination/BOARD.md). Интерфейс `web/` делает Codex (решение Нуржана). Роль напарницы ниже устарела и уточняется Нуржаном.

### Нуржан: ML, оценка и бэкенд (`backend/`)

1. Клиент API организаторов: загрузка DEV и контрольной группы по `group_id` (адрес из `.env`).
2. Judge: по одному вызову LLM на критерий, ответ строго в JSON, цитата-доказательство до вердикта. См. [ML_APPROACH.md](ML_APPROACH.md).
3. Scoring: формула итога, N/A, секции, флаг грубой ошибки, тесты. См. [SCORING.md](SCORING.md).
4. REST API по [API_CONTRACT.md](API_CONTRACT.md) и хранилище (JSON-файлы). Эндпоинты чек-листа и апелляций простые, их делаем после основного пути.
5. Правила под звонки (устная речь, паузы) и под языки RU, KZ, EN.
6. Калибровка: ручная разметка 15–20 диалогов DEV и подбор промптов по ней.
7. Выбор модели, оценка стоимости одной полной оценки.

### Напарница: интерфейс (`web/`)

1. Интерфейс на HTML/CSS/JS (TypeScript с Tailwind допустим): список диалогов, просмотр транскрипта, запуск оценки.
2. Редактор чек-листа с сохранением через `PUT /api/checklist`.
3. Карточка результата: критерий, ответ, вес, объяснение, переход к реплике, итог и секции.
4. Плеер звонка и переход от критерия к реплике и к месту записи.
5. Апелляция: форма подачи и отдельный экран решения проверяющего, исходная и финальная оценка, пересчитанный итог.
6. Моки JSON по контракту в `web/mock/`, пока бэкенд не готов. Переключение мок/реальный API одним флагом.

### Вместе

- Контракт JSON и эндпоинты (первый час).
- Сквозной сценарий и репетиция защиты.
- README и публичный репозиторий.

## Стык

Единственная связь между ролями: форматы в [API_CONTRACT.md](API_CONTRACT.md). Пересчёт итога после апелляции делает функция `scoring` на бэкенде, копии формулы на фронтенде нет.
Пока бэкенд не готов, напарница работает на моках из `web/mock/`. Мок результата имеет `"mock": true`.
Риск: на Нуржане и модель, и бэкенд. Если к 23:00 бэкенд отстаёт, напарница берёт на себя хранилище и эндпоинты апелляций и чек-листа (на Python или Node, по обстоятельствам).

## Критерий готовности (до стоп-кода)

- [ ] Публичный репозиторий, README с запуском.
- [ ] Ссылка на репозиторий отправлена организаторам заранее, до стоп-кода (требование guide).
- [ ] Контрольные диалоги запущены сразу после открытия, результаты готовы к выступлению.
- [ ] Заменённый организаторами критерий сохраняется через интерфейс и применяется к выданным диалогам.
- [ ] Подача апелляции и её проверка сделаны отдельными действиями в интерфейсе, без авторизации.
- [ ] Фронтенд ходит только в наш `/api`, не в API организаторов (CORS).
- [ ] Структура интерфейса допускает адаптацию как HTML-компонента Dynamics 365.
- [ ] Оценка любого диалога из API проходит от начала до конца.
- [ ] Изменённый в интерфейсе критерий применяется при следующей оценке.
- [ ] Апелляция пересчитывает итог.
- [ ] В репозитории нет транскриптов, подписанных ссылок и ключей.
- [ ] В README указаны модель и стоимость одной оценки.
