# Формат выгрузки CQA и контрольный прогон

Контракт взят из `CQA_Student_Guide_Appendix_Results.pdf`, стр. 1–3. Выберите один способ запуска PROD до первого вызова модели.

## Оценка с проверкой в интерфейсе

Запустите Rust-сервер из подготовленной к сдаче копии проекта. Для запуска из пользовательской конфигурации укажите полный адрес PROD, выданный организаторами, как `CONTROL_API_URL`. Убедитесь, что сервер слушает `127.0.0.1:8080` и показывает `judge: openai:gpt-6.1-terra`.

Загрузите контрольную группу через `GET /api/conversations?group=control&refresh=true`. Откройте интерфейс этого же сервера, выберите `control` и проверьте, что видны 10 чатов и открывается транскрипт. Запустите из корня той копии проекта, в которую нужно записать файл результатов:

```powershell
py -3 -B .\tools\cqa_results.py --group prod --team-name Phoenix --expected-model gpt-6.1-terra --model-mode external_api --base-url http://127.0.0.1:8080 --concurrency 3 --no-refresh
```

Эта команда сама оценивает все 10 чатов через указанный сервер и сохраняет результаты для интерфейса. Для проверки после завершения обновите страницу и откройте сохранённую оценку. Сравните `score.final_score` с итогом карточки. Для машинной сверки всех 10 итогов используйте `GET /api/evaluations/{conversation_id}` того же сервера и поле `total`.

## Автономная оценка и выгрузка

Запустите команду из корня копии проекта с финальными бэкендом и чек-листом.

```powershell
py -3 -B .\tools\run_cqa.py prod --concurrency 3
```

Вставьте полный адрес PROD по скрытому запросу. Если настройки бэкенда лежат в другой локальной папке, укажите её через `--config-dir`. Этот параметр задаёт каталог запуска бэкенда. Код, встроенный чек-лист и шаблоны промптов берутся из копии со скриптом. При заданном в процессе `CONTROL_API_URL` скрипт использует его сразу.

Обёртка запускает собственный временный сервер и выгружает результаты за один прогон. Экспортёр сверяет итог с ответом этого экземпляра. Временные оценки недоступны основному интерфейсу после завершения. Для сверки с карточками используйте сценарий с одним общим сервером выше.

## JSON 1.0

В корне проекта должны лежать `results/dev/results.json` для 60 DEV-чатов и 5 звонков и `results/prod/results.json` для 10 контрольных чатов. Корневой объект содержит четыре поля. Это `schema_version` со строкой `"1.0"`, `team_name`, `model` с полями `mode` и `name`, массив `results`. Для Phoenix на Terra поле `model` равно `{"mode":"external_api","name":"gpt-6.1-terra"}`. В DEV-выгрузке, полученной на Luna, указывается фактически использованная Luna.

У каждого диалога исходный `conversation_id` и один `status`. Строка `ok` содержит восемь элементов `criteria` и объект `score`. Элемент критерия содержит `criterion_id`, `value`, краткое `rationale` и `evidence_turns`.

| Критерий | Допустимый `value` | Вес |
|---|---|---:|
| `contact` | `true`, `false` | 10 |
| `discovery` | `true`, `false`, `null` | 15 |
| `identification` | `true`, `false`, `null` | 20 |
| `consultation` | `0`, `5`, `10`, `15`, `20`, `null` | 20 |
| `empathy` | `true`, `false` | 15 |
| `dialogue` | `0`, `4`, `7`, `10` | 15 |
| `closure` | `true`, `false`, `null` | 5 |
| `critical` | `true`, `false` | — |

`null` означает N/A. Число в `value` представляет исходную ступень шкалы. Экспортёр переводит шкальные ответы в доли веса, исключает N/A из суммы применимых весов, масштабирует итог до 100 и округляет его до двух знаков. `score.critical_flag` совпадает с `critical.value` и хранится отдельно от `score.final_score`.

`evidence_turns` содержит номера с 1 в исходном массиве транскрипта, включая сообщения клиента, бота и системы. Дословную цитату проверяет бэкенд и показывает интерфейс. В выгрузке для неё предусмотрен номер реплики и краткое основание. В текущем интерфейсе Дарии номер JSON `4` соответствует подписи `#3`.

При сбое отдельного диалога схема допускает `status: "error"` с тем же ID, пустым `criteria`, `score: null` и причиной в `error`. Системный сбой или несовпадение модели останавливает выгрузку. Успешный выход процесса возможен при отдельных строках `error`, поэтому проверяйте счётчики.

## Приёмка

- В логе завершения `done ok=10 errors=0`. В UTF-8 JSON 10 уникальных исходных ID контрольных чатов и 8 различных критериев для каждого `ok`.
- Проверьте краткие обоснования и номера подтверждающих реплик. Сопоставьте их с полным транскриптом и сравните итог с оценкой того же прогона. При запуске через общий сервер сверяйте карточку или API сохранённых оценок.
- В итоговый открытый репозиторий до стоп-кода должны попасть оба проверенных `results.json`. В проекте `results/` игнорируется Git, поэтому включение этих двух файлов требует явного выбора при согласованной публикации.
